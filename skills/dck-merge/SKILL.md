# dck-merge — 병합·판정

앞의 두 단계가 만든 것을 **만들지 않은 쪽이** 대조한다. 생산자가 자기 산출을 채점하면 같은 맹점이 검증을 그대로 통과한다.

**이 스킬은 새로 판정하지 않는다.** 문서를 읽지 않고, 축의 판정 기준을 다시 적용하지 않는다. 하는 일은 대조·접기·집계다.

## 실행

```bash
node <kit>/core/merge.mjs --config <dck.config.json> --repo <레포 루트> --run-id <id> [--out <디렉토리>] [--waive <코드>]...
```

stdout 으로 `report.md` 가 그대로 나오고, `<out>/<run-id>/report.json` 과 `report.md` 에 남는다.

| 코드 | 뜻 |
|------|-----|
| 0 | pass — 차단급 없음 |
| 1 | fail — 차단급이 하나라도 있음 |
| 2 | 병합기 자체가 못 돌았다 |

## 기대 축은 매니페스트가 정한다

돌아야 할 축 목록을 `scan.json` 에서 가져오지 않는다. **config + 매니페스트를 직접 다시 읽는다.** 스캔 결과를 기준으로 삼으면 "스캔에 안 뜬 축" 이 애초에 기대되지 않아, 축이 통째로 빠진 것을 영원히 못 잡는다.

축마다 스크립트 쪽과 계약 쪽을 따로 확인한다.

| 상황 | 주입되는 지적 |
|------|---------------|
| 활성 축인데 스캔 결과가 없거나 crashed | `coverage.missing` (block) |
| 계약을 가진 활성 축인데 verdict 파일이 없음 | `coverage.missing` (block) |
| verdict 가 형식 위반 / 축 이름 불일치 | `coverage.invalid-verdict` (block) — 그 축의 판정은 **통째로** 버린다 |
| 등록되지 않았거나 건너뛴 축의 verdict 파일이 있음 | `coverage.unexpected-verdict` — 내용은 반영하지 않는다 |
| `when.requires` 미충족으로 skipped | 차단 아님. 사유와 함께 리포트에 남는다 |

`coverage.*` 는 **접히지 않는다.** "이 축은 판정 자체가 없었다" 는 축마다 별개 사실이라 한 건으로 뭉치면 몇 개 축이 빠졌는지 사라진다.

## 접기

같은 `(code, 첫 위치의 파일, 줄)` 은 한 건으로 접고, 잡아낸 축들을 `found_by` 에 남긴다. 심각도는 높은 쪽을 따른다. 결정 축과 판단 축이 같은 줄을 독립적으로 잡았다면 그것은 중복이 아니라 **확신도 신호**다 — 지우지 말고 발견자로 남긴다.

## 축이 자기 결과를 통과시키지 못한다

읽어들인 verdict 에서 다음 키를 **먼저 떼어낸다**: `_demoted`, `demoted`, `_waived`, `waived`, `suppressed`, `severity_cap`, `found_by`. 뗀 건수는 리포트에 그대로 적는다 — 조용히 버리면 축이 계속 시도한다.

- 심각도 상한은 매니페스트의 `severity_cap` 이 정본이다. 축이 신고한 값이 그보다 높으면 잘린다.
- 강등은 **`--waive <코드>` 로만** 들어온다. 명시적으로 남고 리포트에 적용 건수가 찍힌다.
- `--waive coverage.*` 는 거부한다. 검증 못 한 축을 통과로 바꾸는 것이 이 게이트가 막는 바로 그것이다.

## 리포트

`report.md` 는 사람이 읽는 순서로 낸다 — 결과 한 줄, 축 전수 표(종류·상태·스크립트/판정 결과·지적 수), 결과가 없는 축, 지적 목록(block → warn → info), 떼어낸 자기 신고, 적용된 강등.

축 표는 **건너뛴 축과 깨진 축까지 전부** 싣는다. 결과가 없는 축이 목록에서 사라지는 것이 조용한 통과의 정확한 형태다.
