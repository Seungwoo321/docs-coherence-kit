# dck-judge — 판단 단계 (격리 팬아웃)

사람 언어의 의미를 봐야 판정되는 축을 돌린다. 판정 기준은 각 축의 `contract.md` 가 소유한다 — **이 스킬은 계약을 해석하지도, 대신 판정하지도 않는다.** 하는 일은 축마다 격리된 판정자를 띄우고, 그 판정이 약속된 파일로 떨어지게 하는 것뿐이다.

입력은 `scan.json` 의 `awaiting_verdicts` 다. 그 목록에 없는 축을 임의로 추가하거나 빼지 않는다.

## 판정자 격리 — 환경별 수단

축 하나의 판정은 **자기만의 컨텍스트**에서 돈다. 오케스트레이터의 대화 맥락(이미 본 결함, 스캔 요약)이 판정에 스미면 독립 검증이 아니다. 수단은 에이전트 환경이 가진 것을 쓴다:

- **병렬 서브에이전트가 있는 환경** (Claude Code 등) — 축마다 서브에이전트를 띄운다.
- **서브에이전트가 없는 환경** (Codex CLI 등) — 축마다 헤드리스 자식 실행을 백그라운드로 띄운다. 예: `codex exec --sandbox workspace-write "<축 프롬프트>" &` 를 축 수만큼 걸고 전부 기다린다. 자식은 부모의 대화를 물려받지 않으므로 격리가 성립한다.

어느 쪽이든 아래 규율은 같다.

## 팬아웃 규율

**1. N 개 축은 동시에 띄운다.**
서브에이전트라면 호출 N 개를 **하나의 메시지 안에 여러 tool_use 로**, 자식 실행이라면 N 개를 백그라운드로 걸고 한 번에 기다린다. 한 번에 하나씩 돌리면 축 수만큼 순차로 늘어난다. 축은 서로 독립이라 순서에 의미가 없다.

**2. 게이트를 판정자로 감싸지 않는다.**
"판정을 모아 통과 여부를 정하는" 일은 판정자에게 맡기지 않는다. 자기 판정을 자기가 채점하는 구조가 되고, 무엇을 못 봤는지가 프롬프트 안에서 사라진다. 통과 판정은 dck-merge 가 파일을 근거로 한다.

**3. 판정은 파일로 쓴다. 말로 돌려받지 않는다.**
각 판정자는 결과를 **`verdict_file` 경로에 JSON 배열로 쓰고**, 회신은 "썼다 / 몇 건" 한 줄이면 된다. 판정 본문을 산문으로 돌려받으면 오케스트레이터 컨텍스트가 축 수만큼 부풀고, 그 내용은 어차피 병합기가 파일에서 다시 읽는다.

**4. 경로는 오케스트레이터가 준다.**
`contract`·`candidates_file`·`verdict_file` 셋 다 `awaiting_verdicts` 에 이미 있다. 판정자가 경로를 짓게 두지 않는다 — 다른 이름으로 쓰면 병합기가 못 찾고, 못 찾은 축은 커버리지 미달로 차단된다.

## 축 프롬프트에 반드시 들어갈 것

계약 내용을 프롬프트에 복사하지 않는다. 계약은 **경로로 주고 읽게** 한다. 대신 다음 다섯 가지를 매번 명시한다.

1. **계약 경로** — `<contract>` 를 먼저 읽고 그 기준으로만 판정한다.
2. **후보 파일 경로** — `<candidates_file>` 이 있으면 **그 후보만** 확인한다. hybrid 축에서 후보를 넘어 문서 전체를 다시 훑는 것은 스크립트가 이미 한 일을 되풀이하는 것이다. 후보 파일이 `null` 이면 판정 축이므로 검사 범위는 config 의 문서 범위다.
3. **검색 범위** — 볼 디렉토리(문서 루트)와 보지 않을 것을 못 박는다. 범위를 안 주면 레포 전체를 훑어 실행 시간이 한 자릿수 배로 늘어난다. 실측으로 가장 크게 갈린 항목이다.
4. **문서 집합의 성격** — 이 문서들이 무엇인지 한 줄(예: "제품 스펙과 결정 기록, 사람이 손으로 쓴다"). 성격을 모르면 판정자가 문서를 처음부터 파악하느라 시간을 쓴다.
5. **기계 생성물 금지** — 판정 대상이 아닌 것을 명시한다. 빌드 산출물·락 파일·자동 생성 문서·`node_modules` 는 읽지 않는다. 여기서 나온 지적은 사람이 고칠 수 없어 전부 소음이다.

여기에 **출력 형식**을 덧붙인다: `schemas/findings.schema.json` 봉투를 따르는 JSON 배열, `axis` 는 파일명과 같은 축 이름, `code` 는 `<축>.<kebab>`.

## 판정자가 못 하는 것

프롬프트에 함께 못 박는다. 병합기가 어차피 떼어내지만, 시도 자체가 없어야 판정이 온전히 반영된다.

- `coverage.*` 코드를 내는 것 — 커버리지는 병합기만 판정한다.
- `_demoted`·`waived`·`found_by` 같은 키를 붙이는 것 — 자기 지적을 스스로 강등하거나 발견자를 자칭할 수 없다. 병합기가 떼어내고 그 사실을 리포트에 남긴다.
- 다른 축 이름으로 판정을 내는 것 — 파일명과 봉투의 `axis` 가 다르면 그 축의 판정은 통째로 버려지고 커버리지 차단이 뜬다.
- 지적이 없다고 파일을 안 쓰는 것 — **빈 배열 `[]` 을 쓴다.** 파일이 없는 것은 "깨끗함" 이 아니라 "판정이 없음" 이고, 그건 차단이다.

## 끝난 뒤

`awaiting_verdicts` 의 모든 축에 대해 파일이 생겼는지만 확인하고 dck-merge 로 넘어간다. **없는 파일을 대신 만들어 채우지 않는다.** 판정자가 죽었으면 그 사실이 커버리지 차단으로 보고돼야 한다 — 빈 배열로 메우면 검증 못 한 축이 통과로 바뀐다.
