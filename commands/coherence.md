# /coherence — 정합성 검사 오케스트레이션

이 커맨드는 **순서와 분기만** 소유한다. 무엇을 결함으로 볼지는 축 스크립트와 계약이 정하고, 통과 여부는 병합기가 정한다. 여기서 문서를 읽거나 판정 기준을 다시 적용하지 않는다.

인자: `$ARGUMENTS`

## 0. 준비

1. 레포 루트에서 `dck.config.json` 을 찾는다. 없으면 **거기서 멈추고** 알린다 — 설정 없이 도는 기본값은 "무엇을 검사하는지 아무도 모르는 검사" 다. `README.md` 의 붙이기 절과 `schemas/config.schema.json` 을 가리킨다.
2. `--run-id` 가 인자에 없으면 만든다: `git rev-parse --short HEAD` 가 되면 그 값, 아니면 `date +%Y%m%dT%H%M%S`. 세 단계가 **같은 run-id** 를 쓴다 — 여기서 한 번 정하고 그대로 넘긴다.
3. `--axes` 가 있으면 그대로 스캔과 병합 **양쪽에** 넘긴다. 한쪽에만 넘기면 기대 축 목록이 어긋나 멀쩡한 축이 커버리지 미달로 잡힌다.

## 1. 결정적 단계 — dck-scan

`dck-scan` 스킬을 부른다.

```bash
node <kit>/core/scan.mjs --config <config> --repo <레포 루트> --run-id <id> [--axes <목록>]
```

## 2. 게이트

종료 코드로 분기한다. **판정을 다시 읽고 스스로 판단하지 않는다.**

- **2** — 스캐너가 못 돌았다. 검사 결과가 아니라 도구 문제다. stderr 를 그대로 보여주고 멈춘다.
- **1** — 차단급 지적이 있거나 축이 깨졌다. **여기서 멈춘다.** 판단 단계를 부르지 않고, `scan.json` 의 차단급 지적과 crashed 축을 사유와 함께 보고한다. 결정적으로 이미 틀린 것이 있는데 의미 판정에 토큰을 쓰지 않는다.
- **0** — 3 단계로 간다.

## 3. 판단 단계 — dck-judge

`scan.json` 의 `awaiting_verdicts` 가 비어 있으면 건너뛰고 4 로 간다.

비어 있지 않으면 `dck-judge` 스킬을 부른다. 스킬이 팬아웃 규율(한 메시지 안 다중 호출, 프롬프트에 넣을 것, 서브에이전트 금지 사항)을 소유한다 — 여기서 되풀이하지 않는다. 이 단계에서 커맨드가 지키는 것은 하나다: **대기 목록에 있는 축 전부를 넘기고, 없는 verdict 를 대신 만들지 않는다.**

## 4. 병합 — dck-merge

`dck-merge` 스킬을 부른다.

```bash
node <kit>/core/merge.mjs --config <config> --repo <레포 루트> --run-id <id> [--axes <목록>] [--waive <코드>]...
```

3 단계를 건너뛰었더라도 **반드시 부른다.** 판정할 것이 없다는 사실 자체를 병합기가 확인해야 한다.

## 5. 보고

`report.md` 를 근거로 요약한다. 순서:

1. 결과 한 줄 — pass / fail, 차단·경고·정보 건수.
2. 차단급 지적 — 파일·줄과 함께. `coverage.*` 는 "이 축은 판정 자체가 없었다" 라는 뜻이니 문서 결함과 섞어 적지 않는다.
3. 결과가 없는 축 — 건너뛴 축은 사유와 함께. **fail 은 아니지만 pass 도 아니다.**
4. 산출 경로 — `<out>/<run-id>/report.md`.

지적을 요약하면서 **심각도를 낮춰 말하지 않는다.** 강등은 `--waive` 로만 들어오고 리포트에 적용 건수가 찍힌다. 문장으로 눅이는 것은 강등이 아니라 은폐다.
